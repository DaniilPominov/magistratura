Источник: `voice_signals/agent/temp`.

Перед каждой сессией загружать `voice_signals/agent/rules/project-agreements.md`.

Предусловие (не подзадача): базовый репозиторий со структурой `src/ scripts/ tests/ configs/ data/ docs/ experiments/`, зафиксированы версия Python, зависимости, политика данных, формат конфигов и контракты данных (`schemas.py`).

## Определение MVP

В этом плане MVP — это локально воспроизводимый контур подготовки и
полуавтоматической разметки речевых событий, а не обученная нейросеть и не
система вывода о когнитивных характеристиках.

MVP принимает каталог WAV и конфигурацию, после чего:

1. проверяет входные файлы;
2. извлекает единые кадровые признаки;
3. запускает хотя бы energy VAD и один основной VAD backend;
4. формирует непересекающиеся pseudo-labels четырёх классов;
5. экспортирует их в Label Studio как черновики;
6. импортирует исправленную разметку обратно в `SegmentRecord`;
7. считает согласованные метрики на синтетическом корпусе;
8. воспроизводит прогон по конфигурации и seed.

В MVP не входят:

- Hurst, entropy, RQA и Lyapunov как обязательные признаки;
- обучение нейросети;
- оценка связи с когнитивными тестами;
- обязательная обработка реального корпуса до прохождения локального
  synthetic gate;
- обязательная зависимость от облачных сервисов.

### MVP-gate

MVP считается готовым только если одной локальной командой проходят:

```text
synthetic generation
→ audit
→ features
→ VAD
→ pseudo-labels
→ Label Studio export/import round-trip
→ metrics
```

Минимальные проверяемые условия:

- нет пересекающихся сегментов;
- все времена в секундах и находятся в пределах файла;
- pseudo-labels имеют `is_pseudo_label=true`, confidence и provenance;
- повреждённый WAV не останавливает пакетный прогон;
- отчёты и метрики повторяются при одинаковом seed и конфигурации;
- синтетические quality thresholds из TASK-07 явно измеряются, а не только
  проверяется успешное завершение программы.

## Важно: нумерация не задаёт порядок выполнения

Номера TASK-01--TASK-09 являются идентификаторами карточек, а не
хронологическим планом. Порядок ниже учитывает зависимости, критический путь
до разметки и риск преждевременной интеграции исследовательских признаков.

## P0. Предусловие

P0 теперь является обязательной подготовительной задачей и фиксируется
отдельной карточкой [TASK-00-project-bootstrap.md](TASK-00-project-bootstrap.md).

До начала задач зафиксировать единые контракты данных:

```text
FileAuditRecord
FrameFeatureRecord
SegmentRecord
ExperimentRecord
```

Критерий готовности: создан минимальный проектный каркас, зафиксированы
версия Python и зависимости, есть `schemas.py`, базовая конфигурация,
команда тестов и smoke-test импорта. Все модули используют одинаковые
названия полей, единицы времени (секунды), таксономию и правила
версионирования конфигураций.


исследовательского слоя и абляций, но не для первого рабочего

## Границы версий задач

- **TASK-09 минимальная** нужна в начале только как тестовый корпус.
- **TASK-09 полная** завершает интеграцию и проверяет весь пайплайн.
- **TASK-07 базовая** работает без Hurst, entropy и Lyapunov.
- **TASK-07 расширенная** подключает динамические признаки после их валидации.
- Реальный запуск TASK-01 выполняется после получения корпуса; до этого
  реализуется и тестируется версия на синтетических данных.

Нельзя считать pseudo-labels gold-разметкой. Нельзя начинать обучение
нейросети до пилотной разметки и проверки межразметочного согласия. Нельзя
объявлять MVP готовым только потому, что отдельные модули импортируются:
обязателен сквозной локальный прогон.

## Решения, которые принимает человек до старта

1. Таксономия MVP: `speech`, `silent_pause`, `hesitation`, `artifact`.
2. Дыхание: `breath -> artifact` (или отдельный класс `breath`, если научрук требует).
3. Лексические заполнители: не выделять отдельно, инструкция разметки должна быть явной.
4. Прямой Ляпунов: optional exploratory feature; основные признаки — Hurst, entropy, RQA.
5. Первичная метрика статьи: `false_pause_precision`, при контроле `hesitation_recall`, `speech_recall`, `pause_duration_bias`.

До начала реализации MVP человек также должен подтвердить:

6. основной VAD backend для MVP (рекомендуется energy + WebRTC; Silero —
   дополнительный backend при доступности зависимостей);
7. допустимость установки локальных зависимостей и запуска Label Studio;
8. synthetic thresholds для MVP-gate. Если реальных данных ещё нет, они
   оценивают только инженерную работоспособность и не являются утверждением
   о качестве на реальном корпусе.
