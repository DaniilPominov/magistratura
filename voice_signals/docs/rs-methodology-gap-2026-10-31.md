## 2. Как ветвь работает сейчас

Разделения «функция» и «протокол применения» в коде нет: `modified_rs_hurst`
ничего не знает о сегментации, а сегментацию задают скрипты-обвязки.

```
WAV ──> EnergyVad.process_file ──> list[SegmentRecord]
 │
 ├──> audio[start:end] (для каждого сегмента)
 │         └──> modified_rs_hurst(slice, sr) ──> H, T, R² на ОДИН сегмент
```

Точка, где появляется «по сегментам» — `scripts/run_modified_rs.py:113-125`:
цикл по найденным сегментам, вырезка `audio[start:end]`, отдельный вызов
`analyze(...)` на каждом куске. То же в `scripts/demo_pipeline.py:67-75`
(там только первый сегмент). Флаг `--all` прогоняет цикл по всем сегментам
записи.

Внутри одного вызова (`src/voice_signals/dynamics.py:23-117`):

1. огибающая — RMS в **неперекрывающихся** окнах
   `envelope_window_sec = 0.025` (25 мс, `dynamics.py:58-62`);
2. защиты: `len(values) < 16`, `len(envelope) < 8`, константный сигнал →
   `valid=False`;
3. шкала `tau` — `range(max(2, min_tau), len(envelope)//2 + 1)`, то есть
   `min_tau = 4` и верхняя граница = половина длины огибающей **этого
   сегмента** (`dynamics.py:67-68`);
4. для каждого `tau` — перекрывающиеся окна с шагом `tau//2`, центрирование,
   накопленное отклонение, `R = max − min`, деление на СКО, усреднение `R/S`
   по окнам (`dynamics.py:72-90`);
5. `H` — МНК-наклон `ln(R/S)` от `ln(tau/2)` по **всем** точкам сразу
   (`dynamics.py:94-100`);
6. `T` — при `use_piecewise_fit=True` перебор точки излома двух независимых
   МНК-прямых, минимизирующий суммарный остаток; возвращается
   `tau_излома * envelope_window_sec` (`dynamics.py:104-113`, `120-180`);
7. `R² < 0.7` → только warning `weak_log_log_fit`, результат остаётся
   `valid=True`.

## 3. Сопоставление с опорной статьёй

| Аспект | Кузенков/Логинов (2014) | Сейчас в проекте |
|---|---|---|
| Что за ряд | огибающая **всего** речевого материала (чтение/пересказ) | огибающая **отдельного speech-сегмента** |
| `N` в формулах | длина всей записи (минуты) | длина сегмента (0.1–3 с) |
| Верхняя граница `tau` | `N` (шкала идёт до длины ряда) | `len(envelope)//2`, зависит от длины сегмента |
| Шкала `tau` | геометрическая прогрессия, `tau1 = 3`, интерполяция между `floor/ceil` | арифметическая `range(4, N/2+1)` — **геометрической сетки в коде нет** |
| Окно огибающей | 100 мс | 25 мс |
| Усреднение `R/S` | по `k` перекрывающимся интервалам | по перекрывающимся, шаг `tau//2` — близко |
| `H` | показатель на соответствующем режиме | глобальный наклон по всей кривой, включая оба режима, для которых отдельно ищется излом |
| `T` | момент смены режима кусочно-полиномиальной аппроксимацией | излом двух **линейных** МНК (не полиномиальный) |
| Что попадает в ряд | речь **вместе с паузами** (чередование — источник длинных корреляций) | только речь, паузы вырезаны VAD |

Два пункта принципиальны.

**1. Паузы вырезаются.** В статье длиннопериодная корреляция огибающей — это
во многом структура чередования речь / пауза / дыхание на уровне всей записи.
Разрезав запись на speech-сегменты, проект измеряет внутрисегментную
динамику фрагментов и систематически лишает ряд того масштаба, ради которого
метод и применялся. Это не «тот же показатель, посчитанный помельче», а
другая величина.

**2. Верхняя граница `tau` привязана к длине сегмента.** Для сегмента 0.65 с
при 25 мс огибающая — около 26 точек, значит `tau` идёт 4…13: примерно 10
масштабов, и на больших `tau` остаётся 2–3 перекрывающихся окна. Оценки `H` и
`T` становятся функцией длины входа.

## 4. Наблюдаемые следствия

Измерено в Iteration 02 и зафиксировано в
[scientific-report-2026-10-23.tex:421-465](../reports/scientific-report-2026-10-23.tex)
и [advisor-briefing-2026-10-17.md:101-109](advisor-briefing-2026-10-17.md):

- короткие сегменты: `H ≈ 0.95–0.99`;
- длинные сегменты: `H ≈ 0.69–0.87`;
- корреляция `H` с длиной сегмента ≈ −0.76;
- корреляция `T` с числом доступных масштабов ≈ +0.87, то есть `T` фактически
  воспроизводит длину сегмента, а не является от неё независимой
  характеристикой;
- при окне огибающей 100 мс (как в статье) `H` снижается до ≈ 0.4–0.9,
  `T` попадает в диапазон статьи ≈ 0.6–2.0 с, но валидными остаются 19
  сегментов из 79 (остальные короче ≈ 1.2 с).

Дополнительно: в самой статье `H` во всех клинических группах равен
0.984–0.991, то есть `H` не дискриминативен и там; различающим параметром
выступает `T`. В проекте же `T` в текущем протоколе в основном кодирует длину
входа.

## 6. Вывод

Ветвь не «бесполезна»: `modified_rs_hurst` — корректная, детерминированная,
покрытая тестами реализация R/S с флагами валидности, а вход
`precomputed_envelope` и параметр `max_tau` позволяют считать её на любом ряде
с любым диапазоном. То есть **функция шире, чем текущий протокол её
использования**.

Но в текущей конфигурации (per-segment + `tau` до `N/2` + окно 25 мс) ветвь
**не является измерительным инструментом**:

- `H` в насыщении (≈ 0.95–0.99) и не имеет диапазона для различения;
- `T` в основном кодирует длину сегмента (корреляция с числом масштабов
  ≈ +0.87);
- 79 сегментов одной записи не являются независимыми наблюдениями.

Практическое следствие:

- значения `H`/`T` **нельзя сравнивать между сегментами разной длины**;
- значения `H`/`T` **нельзя сравнивать с таблицей 1 статьи** — там другой
  `N`, другое окно огибающей и другой вход (с паузами);
- per-segment значения остаются допустимым выходом ветви признаков, но только
  с явной пометкой о несопоставимости и с длиной сегмента как ковариатой.

## 7. Варианты протокола

Три взаимоисключающих варианта были сформулированы как опции; **выбрана и
реализована комбинация A + C** (31.10.2026).

**A. Как в статье: один ряд на запись. [РЕАЛИЗОВАНО]**
Огибающая всего файла (с паузами), окно 100 мс, `tau` до `N`.
Даёт `H`/`T`, сопоставимые с Кузенковым. Не даёт per-segment признаков.
Реализация: `modified_rs_hurst_full_record()` в `dynamics.py`.

**B. Фиксированные скользящие окна. [НЕ РЕАЛИЗОВАНО]**
Окна одинаковой длины с фиксированным сверху `max_tau`.
Значения сравнимы между окнами внутри записи и между записями. Отклонён в
пользу A+C; при необходимости можно добавить позже как третий `scope`.

**C. Per-segment как отдельный признак. [РЕАЛИЗОВАНО]**
Текущий расчёт оставлен, но явно отделён от оценки «по статье»: результат
несёт поля `scope="segment"` и `comparable_to_reference=False`, плюс
`input_length_sec` как ковариата. Реализация: `modified_rs_hurst()` (прежнее
имя и сигнатура сохранены, добавлены новые поля/параметры).

**Итог:** A и C — две разные величины с разными именами функций и
отдельными полями в `HurstRSResult` (`scope`, `comparable_to_reference`).
Несмешиваемость закреплена в типе результата, а не только в соглашении.
Решение подтверждено пользователем проекта 31.10.2026 без дополнительного
согласования с научным руководителем (ср. [questions-for-advisor.md](questions-for-advisor.md),
п. 5.1 — вопрос к руководителю остаётся открытым для последующей валидации
выбора, но не блокирует реализацию).

### Новые поля `HurstRSResult`

- `scope: str` — `"segment"` или `"full_record"`.
- `comparable_to_reference: bool` — `True` только для `full_record`.
- `input_length_sec: float | None` — длина входного ряда в секундах,
  ковариата для варианта C.
- `tau_scale: str` — `"arithmetic"` или `"geometric"`.

  `modified_rs_hurst_full_record()` (вариант A).
- `configs/default.yaml` — `dynamics.modified_rs.segment` /
  `.full_record`.
- `scripts/run_modified_rs.py`, `scripts/demo_pipeline.py` — оба протокола.
- `tests/test_vad.py` — тесты на geometric scale, full_record scope,
